# Agent 驱动型电商 CLI 设计与开发规范

<!-- coverage: KU-01 KU-02 KU-03 KU-04 KU-05 KU-06 KU-07 KU-08 KU-09 KU-10 KU-11 KU-12 KU-13 KU-14 KU-15 KU-16 KU-17 KU-18 KU-19 KU-20 KU-21 KU-22 -->

## 1. 规范目的

本规范用于开发面向 Agent 的电商渠道 CLI，例如：

- `tbcli`：淘宝/天猫；
- `dycli`：抖音电商；
- `jdcli`：京东；
- `alicli`：1688 或阿里巴巴相关业务；
- 未来其他平台、ERP、物流、广告或商家后台 CLI。

它不规定某个平台的具体接口、选择器或登录页面，而是定义所有同类 CLI 共同遵守的产品、执行、安全、数据、测试和发布契约。

核心目标是：

> 让业务人员用自然语言提出目标，让 Agent 能发现正确能力，让 CLI 以可验证、可停止、可测试的方式完成确定性执行。

## 2. 适用边界

### 2.1 适用任务

- 获取店铺、商品、订单、物流、推广、财务或经营数据；
- 把结构化数据整理为 Excel、CSV、JSON 或业务报告；
- 在已授权的商家后台填写、创建、更新或提交数据；
- 使用网页登录态调用页面中的结构化能力；
- 把探索成功的网页/API能力沉淀为团队可安装的工具。

### 2.2 不允许的用途

- 绕过验证码、滑块、安全验证、访问限制或平台风控；
- 获取用户无权访问的数据；
- 导出、传播或写入 Cookie、Token、密码等认证材料；
- 伪造商品、价格、库存、订单、店铺或操作成功状态；
- 把网页结构偶然可用当成永久稳定接口；
- 在用户未确认时执行高影响写入、退款、改价、删除或发布。

## 3. 总体架构

```text
业务用户
  ↓ 自然语言目标
Agent 认知与编排层
  ↓ capabilities --json / 稳定命令
CLI 业务命令层
  ↓ 公共安全与会话策略
渠道适配层
  ↓ 官方API / 页面结构化请求 / 浏览器运行时 / 页面渲染
电商平台
  ↓ 原始结果
规范化与交付层
  ↓
JSON / CSV / Excel / 业务结果
```

### 3.1 Agent 的职责

- 理解用户业务目标；
- 查询 CLI 当前能力；
- 收集缺少的输入；
- 选择稳定命令，不猜测参数；
- 识别只读、写入和高影响操作；
- 需要时取得用户确认；
- 解释失败原因并交付结果。

### 3.2 CLI 的职责

- 参数解析与校验；
- 环境、浏览器和登录状态检查；
- 请求延时、验证停止与错误码；
- 渠道调用、分页、重试和数据规范化；
- 输出文件与机器可读结果；
- 对副作用、失败和部分结果给出确定状态；
- 保持可重复调用和可测试。

### 3.3 渠道适配器的职责

- 平台域名、浏览器入口和登录识别；
- 官方或页面结构化请求协议；
- 签名、分页、字段和状态映射；
- 页面风险与验证信号；
- 平台特有数据还原；
- 写入动作的提交、回读和幂等实现。

核心层不得散落淘宝、抖音、京东或1688的硬编码。平台差异进入适配器。

## 4. 规范用语

- **必须（MUST）**：缺失即不允许发布。
- **应该（SHOULD）**：原则上必须，只有明确记录原因时才能例外。
- **可以（MAY）**：按任务复杂度选择。

## 5. 能力自描述契约

### 5.1 必须提供两类入口

```bash
channelcli capabilities
channelcli capabilities --json
```

- 默认输出面向电商业务人员；
- JSON 输出面向 Agent；
- 可以提供 `--all` 展示内部与开发能力。

用户不应先学习命令，而应能够问：

> 这个 CLI 有哪些能力？

### 5.2 每项业务能力必须登记

| 字段 | 含义 |
| --- | --- |
| `id` | 跨版本稳定的能力标识 |
| `name` | 电商业务名称 |
| `description` | 能解决什么业务问题 |
| `examplePrompt` | 用户可直接对 Agent 说的话 |
| `requiredInputs` | 执行前必须提供的信息 |
| `optionalInputs` | 可选范围、页数、时间等 |
| `delivery` | 最终交付物 |
| `commandTemplate` | Agent 调用模板 |
| `maturity` | stable / experimental / development |
| `riskLevel` | read / write / high-impact |

示例：

```json
{
  "id": "shop-products",
  "name": "获取店铺商品列表",
  "description": "获取店铺商品、价格、销量、链接、图片和SKU信息。",
  "examplePrompt": "帮我获取【店铺首页链接】的商品列表",
  "requiredInputs": ["店铺首页链接"],
  "optionalInputs": ["最多获取多少页"],
  "delivery": "Excel商品列表",
  "commandTemplate": "channelcli shop products --url <链接> --out <文件.xlsx>",
  "maturity": "stable",
  "riskLevel": "read"
}
```

### 5.3 单一事实源

能力注册表必须同时驱动：

- CLI 路由；
- `capabilities` 输出；
- Agent JSON；
- 帮助文本；
- 能力完整性测试。

不得在 README、帮助文本、Skill 和代码里分别维护互相独立的能力列表。

### 5.4 三类能力分层

| 类型 | 例子 | 默认是否展示 |
| --- | --- | --- |
| 业务能力 | 获取商品、查询物流、填写活动 | 是 |
| 内部能力 | 打开浏览器、doctor、检查版本 | 否 |
| 开发能力 | 检查页面、捕获元数据、接口探测 | 否 |

业务描述不应出现 API、CDP、selector、拦截、解码等实现术语。

## 6. 命令与进程契约

每个稳定命令必须具备：

- 清晰的 command/subcommand；
- `--help`；
- 可选 `--json`；
- 参数类型、范围和缺失提示；
- 稳定字段和必要的 schema/version；
- 非零失败退出码；
- stdout 输出结果，stderr 输出进度；
- 明确的超时、重试和停止条件；
- 输出路径回显；
- 不在日志中泄露凭证和敏感参数。

推荐统一错误码：

| 错误码 | 含义 | Agent动作 |
| --- | --- | --- |
| `INPUT_REQUIRED` | 缺少必要输入 | 只追问缺少字段 |
| `ENVIRONMENT_ERROR` | 浏览器或依赖不可用 | 引导修复环境 |
| `AUTH_REQUIRED` | 未登录或登录失效 | 停止，要求人工登录 |
| `VERIFICATION_REQUIRED` | 验证码、滑块或风控 | 立即停止，人工处理 |
| `RATE_LIMITED` | 平台限流 | 停止并告知等待 |
| `PARTIAL_DATA` | 数据不完整 | 不宣称完整成功 |
| `WRITE_CONFIRMATION_REQUIRED` | 写入待确认 | 展示预览并等待确认 |
| `WRITE_RESULT_UNVERIFIED` | 已提交但无法回读确认 | 标记未知，不重复提交 |

## 7. 浏览器与登录态

### 7.1 专用持久浏览器身份

需要网页登录态时，CLI 应使用专用、持久的浏览器 Profile：

- 与用户普通浏览器隔离；
- 同一渠道的可信 CLI 可以复用；
- 登录一次后保留会话；
- Profile、调试端口和浏览器路径可配置；
- 不为每次任务创建临时身份；
- 不把个人机器绝对路径写进可分享包。

### 7.2 凭证边界

- CLI 不导出或另存 Cookie；
- 不在 stdout、日志、Excel、错误栈中打印认证材料；
- 请求尽量在已登录页面上下文中执行；
- 如果必须使用 Token，交给系统密钥库、OAuth或专用配置；
- 卸载代码和撤销授权是两个独立动作。

### 7.3 首次登录

最低可接受流程：

1. 自动打开专用浏览器；
2. 检测未登录；
3. 停止数据请求；
4. 提示用户人工登录；
5. 用户登录后重新执行。

若以后实现等待与恢复，必须设置明确超时、只监听登录完成、不在验证页面继续请求，并防止恢复后重复写入。

## 8. 读取请求安全协议

### 8.1 每次请求的强制顺序

```text
确认授权范围
→ 检查登录
→ 检查验证/风控
→ 随机延时
→ 再次检查验证/风控
→ 发送一次请求
→ 检查响应与页面状态
→ 决定继续、有限重试或停止
```

### 8.2 随机延时

- 每次数据 API 请求前必须随机等待；
- 每次重试也必须重新等待；
- 通用默认起点可采用 1000—2000ms；
- 平台规则、接口配额或业务风险要求更严格时采用更慢策略；
- 延时范围应可配置，但不得通过配置关闭其他安全检查；
- 随机延时不是规避平台风控的保证，只是请求节奏控制的一部分。

### 8.3 立即停止信号

发现以下任一情况必须立即停止：

- 未登录或登录重定向；
- 验证码、滑块、人机验证；
- 安全验证、访问受限、处罚页；
- 会话过期、非法访问；
- 平台明确的用户校验或风控错误；
- 页面状态无法可靠读取；
- 当前账号无权限访问目标数据。

停止后禁止：

- 自动刷新验证页；
- 自动绕过验证；
- 继续下一页；
- 对同一风险错误反复重试；
- 改用搜索引擎或其他账号旁路；
- 把部分结果伪装成完整结果。

### 8.4 可以重试的错误

只有明确属于瞬时技术错误时才可有限重试，例如网络中断或普通超时。每次重试仍需重新经过登录、验证和随机延时策略。达到次数上限后返回真实错误。

## 9. 网页写入安全协议

读取和写入必须拆成不同命令或明确不同动作，不能让只读命令隐含写入。

### 9.1 风险分级

| 等级 | 例子 | 最低门禁 |
| --- | --- | --- |
| R0 | 本地解析、格式转换 | 可直接执行 |
| R1 | 查询商品、订单、物流 | 登录、延时、验证停止 |
| W1 | 保存草稿、填写未提交表单 | 展示变更摘要，可撤销 |
| W2 | 发布商品、报名活动、修改库存或价格 | 提交前显式确认，提交后回读 |
| W3 | 删除、退款、确认收货、批量改价、资金状态变化 | 二次确认、精确对象、审计与恢复方案 |

### 9.2 写入命令必须具备

- `--dry-run` 或等价预览；
- 变更对象、旧值、新值和影响范围；
- 明确的用户确认；
- 幂等键或防重复提交设计；
- 提交后回读验证；
- 不确定结果使用“未知”，不得自动再次提交；
- 操作时间、对象、结果和错误的审计记录；
- 批量操作的上限、分批和中止机制；
- 能恢复时提供回滚或补偿动作。

## 10. 数据获取优先级

按可靠性和可验证性依次选择：

1. 平台官方、文档化且已授权的 API；
2. 已登录页面实际使用的结构化请求；
3. 页面运行时结构化状态；
4. 真实 DOM 和渲染值；
5. 字体、格式化或前端显示机制的可验证还原；
6. OCR，仅作为最后降级。

禁止为了“拿到数据”无条件跳到视觉识别，因为 OCR 更难保证字段归属、精度和完整性。

### 10.1 展示值与接口值不一致

当接口值不是页面最终显示值时：

1. 确认页面确实显示目标值；
2. 找到浏览器运行时的还原路径；
3. 使用商品ID、订单ID等稳定标识匹配；
4. 为还原逻辑建立独立测试；
5. 不能完整匹配时返回 `PARTIAL_DATA` 或停止交付；
6. 不猜测、不使用相邻元素代替、不静默填空。

tbcli 的价格案例表明，动态字体、页面列表和详情页可以组成可验证的还原链，但具体字体文件和选择器属于淘宝适配器，不属于通用核心。

## 11. 分页、去重与完整性

- 分页以平台响应的下一页信号为准；
- 允许 `--max-pages` 做小范围测试；
- 使用稳定业务ID去重；
- 记录请求页数、返回数、去重数和目标总数；
- 页面展示数量与接口分页不一致时，明确当前采用的口径；
- 输出前执行完整性检查；
- 数据缺失、字段错配或目标数量异常时，不得宣称完整成功。

## 12. 开发模式到稳定命令

### 12.1 开发工具的作用

开发模式可以提供：

- 页面列表；
- 页面环境和必要配置检查；
- 限时捕获请求元数据；
- 响应状态、资源类型和脱敏URL；
- 安全信号观察。

开发工具必须复用稳定命令的浏览器、登录和停止规则。

### 12.2 探索边界

- 捕获范围限定在目标平台；
- 对 Token、sign、session、手机号等参数脱敏；
- 不默认保存响应正文；
- 不导出 Cookie；
- 遇到验证立即停止捕获；
- 探索脚本不得直接成为长期业务入口。

### 12.3 折回稳定命令

一个新需求满足以下条件时，必须进入正式 CLI：

- 已理解输入、输出和失败形态；
- 预计会再次使用；
- 可以定义稳定命令；
- 能实施安全和完整性检查；
- 能写自动测试。

正式化必须同步完成：

1. 命令与参数；
2. 渠道适配器；
3. 规范化输出；
4. 安全策略；
5. 能力注册；
6. 测试；
7. 使用文档；
8. 版本和发布说明。

## 13. 数据与交付分层

### 13.1 三层数据

| 层 | 用途 | 是否面向业务用户 |
| --- | --- | --- |
| 原始层 | 接口响应、调试和证据 | 否 |
| 规范化层 | 跨命令组合、JSON schema | Agent/程序 |
| 交付层 | Excel、报表、业务结果 | 是 |

### 13.2 最终交付原则

- 使用业务名称而不是实现名称；
- 隐藏接口、选择器、编码、解码和风控实现；
- 保留业务复核需要的ID、链接、时间和来源；
- 金额、日期、比例和ID使用正确的数据类型；
- 工作表、字段顺序和命名形成稳定契约；
- 输出文件名可读，并在命令结束时回显绝对路径；
- 技术错误写入日志，不混进业务表格。

例如商品交付可以包含“概览、商品列表、SKU明细”，但不应包含“接口原始编码价格”“页面混淆字符”“请求延时”等内部列。

## 14. 跨平台规范

### 14.1 共同核心

- 业务命令和参数；
- 能力注册表；
- 数据模型；
- 安全策略；
- 渠道适配器接口；
- 导出器；
- 业务契约测试。

### 14.2 系统适配

- 浏览器安装路径；
- Profile和配置目录；
- 路径分隔符与文件名；
- 进程启动；
- 可执行权限；
- 环境变量；
- 编码和终端输出。

平台判断必须集中封装，不得散落在业务命令中。

### 14.3 安装契约

安装说明必须明确：

- 支持的操作系统；
- Node/Python/浏览器等系统前置条件；
- 包管理器自动安装的依赖；
- 首次登录方式；
- doctor/status命令；
- 升级和卸载方式。

## 16. Codex 开发治理

仅依赖“Agent记得规范”是不可靠的。必须形成三层约束：

### 16.1 仓库规则

`AGENTS.md` 至少声明：

- 新业务能力必须登记；
- API必须走公共请求策略；
- 未登录和验证必须停止；
- 写操作风险等级和确认规则；
- 不能长期保留一次性旁路；
- 发布前必须运行的测试。

### 16.2 公共代码

让正确行为成为默认入口：

- `withAuthenticatedSession`；
- `waitBeforeApiRequest`；
- `verificationGuard`；
- 统一错误码；
- 统一能力注册；
- 统一输出与脱敏。

### 16.3 自动测试

测试必须阻止：

- 命令存在但未登记能力；
- 稳定业务能力缺少示例、输入或交付说明；
- API命令绕过公共安全策略；
- 最终Excel出现内部调试列；
- 路由、帮助和注册表不一致；
- 发布包缺少运行文件。

## 17. 测试矩阵

| 层级 | 必测内容 |
| --- | --- |
| 单元测试 | 参数、随机延时边界、登录判断、风险信号、字段映射、脱敏 |
| 契约测试 | capabilities、JSON schema、错误码、stdout/stderr、Excel字段 |
| 渠道适配测试 | 分页、签名、页面状态、展示值还原、写后回读 |
| 负向测试 | 未登录、验证、限流、权限不足、部分数据、重复提交 |
| 跨平台测试 | 路径、Chrome探测、进程启动、编码 |
| 打包测试 | 包内容、依赖、可执行入口 |
| 全新安装测试 | 干净目录安装、help、capabilities、doctor |
| 真实小样本 | 少量授权数据、慢速请求、人工监控 |

真实测试必须使用最小范围，并在登录或验证出现时立即停止。

## 18. 版本与发布

推荐发布链路：

```text
Codex开发
→ 本地测试
→ Pull Request
→ 合并主分支
→ GitHub Release
→ CI重新安装和测试
→ OIDC发布包管理器
→ 公网全新安装验证
```

发布规范：

- 使用语义化版本；
- Release与包版本一致；
- CI执行锁文件安装和完整测试；
- npm等发布优先使用可信发布者/OIDC；
- 不把长期发布Token放在仓库；
- 发布后从公共仓库重新安装验证；
- 同一安装命令同时服务首次安装和升级；
- 权限、认证或输出契约变化必须进入变更说明。

## 19. 新渠道 CLI 的适配清单

开发 `dycli`、`jdcli`、`alicli` 等新工具时逐项回答：

### 产品

- 用户最常说的业务目标是什么？
- 第一个稳定能力是什么？
- 需要什么输入，交付什么文件？

### 会话

- 使用官方API、OAuth还是浏览器登录态？
- 专用Profile如何定位？
- 未登录和过期如何识别？

### 安全

- 平台有哪些验证码、滑块、限流和风控信号？
- 默认请求间隔是多少？
- 哪些错误可以重试，哪些必须停止？

### 数据

- 官方或页面结构化接口是什么？
- 分页、ID和字段如何映射？
- 页面展示值是否经过前端格式化或混淆？
- 如何验证完整性？

### 写入

- 动作风险等级是什么？
- 是否支持dry-run？
- 如何确认、幂等、回读和审计？

### 交付

- Agent需要什么JSON？
- 业务人员需要什么Excel或报告？
- 哪些内部字段必须隐藏？

### 分发

- 支持哪些操作系统？
- 系统前置条件是什么？
- 如何安装、doctor、升级和卸载？

## 20. 新能力完成定义

一个新业务能力只有同时满足以下条件才算完成：

- [ ] 业务名称和边界清楚；
- [ ] 有用户自然语言示例；
- [ ] 必填和可选输入已定义；
- [ ] 命令、参数和帮助可用；
- [ ] 能力注册表已更新；
- [ ] 登录与权限前置检查完成；
- [ ] 每次请求和重试执行随机延时；
- [ ] 验证与风控信号立即停止；
- [ ] 分页、去重和完整性规则明确；
- [ ] 机器输出与业务交付分层；
- [ ] 写入动作具有对应确认等级；
- [ ] 正向与负向测试通过；
- [ ] README和AGENTS已同步；
- [ ] 打包和全新安装验证通过；
- [ ] 真实最小样本验证通过；
- [ ] 版本和发布记录可追踪。

## 21. 常见反模式

- 让用户先学习一长串命令；
- Agent凭记忆猜参数；
- README、Skill和代码各有一份能力列表；
- 普通用户看到API、CDP和选择器术语；
- 每个命令各写一套登录和延时逻辑；
- 遇到风控仍自动重试；
- 接口取不到就直接OCR；
- 把一次性探测脚本当正式能力；
- 把部分成功写成完整成功；
- 写入失败后自动再次提交；
- 最终Excel保留调试字段；
- 只在开发机测试，不验证发布包；
- 依靠Codex记忆规则而没有代码和测试门。

## 22. 当前边界与演化方向

本规范已经覆盖读取型 CLI 的成熟主线。以下属于下一阶段：

- 安全等待首次登录并恢复；
- 多浏览器支持；
- 跨渠道统一能力命名和schema版本；
- 写入事务、回滚和批量中止协议；
- 多CLI共享浏览器与端口注册；
- CLI向MCP或插件分发层演进。

这些目标不能被写成已经实现的现状。具体项目必须以当前代码、`capabilities --json`、版本和测试结果为准。

## 23. 向 Skill 与插件层交接

CLI、Skill 和 Plugin 不是三种互相替代的实现，而是同一能力生命周期中的不同层：

```text
业务需求
→ 开发模式探索
→ 稳定 CLI 能力
→ capabilities 能力注册
→ CLI 契约与安全测试
→ Skill 认知与路由
→ Plugin 安装与分发
```

- CLI 是确定性执行层，负责环境、会话、安全、数据和副作用；
- Skill 是认知与编排层，负责理解意图、收集输入、选择能力和解释结果；
- Plugin 是产品化封装层，负责发现、安装、配置、升级和跨任务加载。

### 23.1 Plugin Readiness Gate

准备把 CLI 接入 Skill 或封装为 Plugin 前，必须确认：

- [ ] `capabilities --json` 是能力清单的单一事实源；
- [ ] 稳定命令具有明确参数、JSON schema、错误码和退出状态；
- [ ] 登录、验证、请求节奏、重试、写入确认和脱敏由公共策略实现；
- [ ] `doctor --json` 或等价命令能给出可解析的环境诊断；
- [ ] Skill 不需要猜测自然语言日志或依赖当前对话记忆；
- [ ] CLI 能在干净环境完成安装、首次运行、升级和卸载；
- [ ] 正向、负向、契约、打包和真实小样本测试均已通过；
- [ ] 当前版本、能力成熟度和未实现边界均可查询。

没有通过此门禁时，应继续修复 CLI 契约，不使用 Manifest、MCP 或 Hook 掩盖执行层的不稳定。

### 23.2 分发边界

- CLI 分发负责 npm、GitHub Release、OIDC、系统依赖和 CLI 版本；
- Plugin 分发负责 Plugin 版本、组件发现、安装生命周期和 Marketplace；
- Plugin 可以依赖独立发布的 CLI，也可以随包携带 Runtime，不能因此产生两套业务实现；
- 具体封装策略、Skill 组织和插件测试见《从 CLI 与 Skill 演进为 Codex 插件》。
