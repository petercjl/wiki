# AI Agent 执行链路审计方法

## 核心判断

任务完成不等于系统工作正常。在 AI Agent 系统中，Agent 选择了什么 Skill、调用了什么工具、经历了哪些失败、采用了什么降级路径、修改了哪些环境，以及是否完成正式验证，本身就是产品质量的一部分。

执行链路审计把质量判断拆成两个相互独立的问题：

1. **结果验收**：用户最终想要的文件、状态或业务结果是否真实存在并符合要求。
2. **过程验收**：Agent 是否沿着受支持、可复现、低副作用、经过验证的路径得到结果。

因此，Agent 最终回复中的“完成”“创建成功”或“验证通过”只能算结果声明，不能单独证明任务真正成功。

## 二维判断模型

| 最终结果 | 执行过程 | 判断 |
|---|---|---|
| 成功 | 合规 | 真成功：结果和过程都可以复现 |
| 成功 | 不合规 | 假成功：结果存在，但依赖绕路、静默降级或跳过验证 |
| 失败 | 合规 | 干净失败：能力边界或前置条件不足被准确报告 |
| 失败 | 不合规 | 系统失败：执行链路本身存在缺口，失败结论也可能不可靠 |

“假成功”是最值得审计的象限。传统测试容易因为最终文件存在而放行，但它可能掩盖高成本解压、偶然环境依赖、未授权安装、标准流程绕过或没有回归验证。

## 基本概念

### 预期主线

根据用户目标、系统 Skill、产品文档、工具协议和安全规则，任务本应经过的主要步骤。预期主线必须包含关键 gate，例如初始化、授权、验证、写盘证明和清理。

### 实际轨迹

从会话日志中还原出的可观察事件序列，包括用户请求、Skill 读取、thinking、工具调用、命令、返回值、文件写入、失败重试、最终回复和副作用。

### 合理分支

系统契约明确允许，并且跨环境可复现的替代路径。合理分支可以偏离主线，但必须在完成后回到主线和验证 gate。

### 绕路

因为工具发现、路径解析、环境识别或产品接口不完整而产生的无效尝试。绕路不一定立即导致失败，但会增加时间、资源和不确定性。

### 静默降级

正式步骤失败后，Agent 未经明确授权或没有上游规则支持，就使用更弱的方法继续，并仍把结果报告为完整成功。

### 契约绕过

系统 Skill 或工具协议明确要求某个步骤，Agent 却跳过或以非等价操作替代。例如初始化脚本失败后，直接手工建立目录和文件。

### 假成功

最终结果表面存在，但过程不满足关键契约、验证或可复现性要求。假成功不是“结果完全没用”，而是不能把这次偶然成功当作产品能力已经成立。

## 证据优先级

审计应按以下优先级判断事实：

1. **工具调用与命令返回值**：调用了什么、退出码是什么、是否报错。
2. **文件和系统副作用**：文件是否真实存在、内容是否正确、环境是否被修改、临时目录是否残留。
3. **可重复验证结果**：校验器、测试、干净会话和端到端输出物检查。
4. **assistant thinking**：用于理解选路原因和发现隐含假设，但不能替代执行证据。
5. **最终回复声明**：只能证明 Agent 如何描述结果，证据强度最低。

thinking 可以完整归档和分析，但核心结论必须能够脱离 thinking，由工具、返回值和副作用独立支撑。这样方法才可迁移到不公开 thinking 的 Agent 平台。

## 九步审计 SOP

### 1. 定义任务目标

写清用户真正要得到的结果、允许的副作用和完成条件。不要直接采用 Agent 最后的自我总结。

### 2. 建立预期主线

读取实际被选中的 Skill、工具说明和产品契约，列出必须经过的节点、可选分支和禁止绕过的 gate。

### 3. 选择可复现样本

优先使用简单、边界清楚的任务作为 canary。简单任务更容易暴露系统成本，也更容易判断某次绕路是否必要。

### 4. 使用干净环境和干净上下文

记录操作系统、产品版本、运行时、已安装工具和会话状态。新对话用于避免设计上下文替 Agent 补齐缺失规则。

### 5. 获取完整执行轨迹

采集用户消息、Skill 选择、thinking、tool call、tool result、退出码、耗时、路径、文件写入和最终回复。保留原始 transcript，只在派生报告中脱敏和归一化。

### 6. 重建时间线

将 tool call 和 tool result 关联，按时间顺序说明“尝试了什么、为什么失败、接下来改走什么路径”。避免只摘取支持既有结论的片段。

### 7. 标记绕路与副作用

逐节点判断它属于主线、合理分支、无效重试、工具缺口、静默降级还是契约绕过。同时检查下载、安装、PATH、权限、完整解压和残留目录。

### 8. 分离结果判定与过程判定

独立检查最终输出物，再独立评估过程。最后使用二维模型给出真成功、假成功、干净失败或系统失败。

### 9. 定位修复层并回归

问题应写回真正拥有它的层级。修复后必须用新对话、相同 canary 和相同证据面重新运行，比较新的执行路径是否更短、更稳定并完成全部 gate。

## 绕路分类

| 分类 | 识别信号 | 常见修复层 |
|---|---|---|
| 环境缺口 | 运行时、PATH、权限或架构不满足 | 环境准备、运行时探测 |
| 工具缺口 | 没有完成动作的正式工具或 API | CLI、MCP、产品工具层 |
| 集成缺口 | 两个组件分别可用，但路径、协议或身份语义不兼容 | 产品集成、打包、注册层 |
| 调度绕路 | 重复探测、错误入口、已有资源未发现 | Agent 路由、环境发现规则 |
| 契约绕过 | 强制步骤失败后被手工操作静默替代 | Skill 主线、产品执行接口 |
| 验证缺失 | 创建了结果但没有执行正式校验或端到端测试 | Skill QA、测试框架 |
| 副作用风险 | 下载、安装、改 PATH、放宽权限、完整解压、残留文件 | 工具实现、安全与清理机制 |

## 合理自适应与问题绕路的边界

大模型能够诊断和绕路是 Agent 的价值，不应把所有重试都定义为缺陷。判断一条替代路径是否合理，至少检查：

- 上游契约是否明确允许；
- 是否使用当前版本的真实能力，而不是冻结副本；
- 是否能在另一台干净机器复现；
- 是否增加了未告知的安装、网络、权限或资源成本；
- 是否完成原主线的验证和清理 gate；
- 是否把部分成功准确报告为部分成功。

只要其中关键项不满足，就不能因为最终产物存在而把过程判为合规。

## 修复层定位

| 现象 | 优先修复位置 |
|---|---|
| 用户目标表达不清 | 提示词或交互设计 |
| Skill 没有写明主线、分支或验证 | Skill |
| Agent 找不到已有命令或反复猜参数 | CLI/工具说明与 Agent 路由 |
| 工具只能读不能执行、路径语义不一致 | 产品集成接口 |
| 打包后 helper 没有真实路径 | 桌面打包和系统 Skill 注册 |
| 成功后没有验证或干净回归 | 测试与 QA |
| 临时目录、安装包或环境修改残留 | 工具清理与事务边界 |

不要用提示词长期补偿产品结构问题，也不要因为模型能临场恢复，就把缺失的产品能力视为已经存在。

## SealSeek Skill Creator 案例

### 背景

SealSeek 能创建 Skill，团队也已经创建过多个 Skill。过去的验收主要看最终 Skill 是否出现，因此没有发现系统 Creator 的标准执行链路存在问题。

### 第一次会话：完整解压后成功初始化

会话 `5138b8fe-7021-45f1-bf1b-7d22d5d737e2` 中：

1. Agent 从 `app.asar` 读取系统 `skill-creator`。
2. Python 不能执行 ASAR 虚拟路径中的 `init_skill.py`。
3. Agent尝试不存在的 unpacked 路径和多个 ASAR 工具入口。
4. PowerShell 的 `npx.ps1` 被执行策略拦截。
5. Agent 最终把约 207 MB 的完整应用 ASAR 解压到工作区。
6. 它从解压目录成功运行当前版本 `init_skill.py`。
7. 最终 Skill 存在，但没有运行 `quick_validate.py`，解压目录也未清理。

结果验收可以通过，过程验收失败，因此属于假成功。

### 第二次会话：不复用已有解压结果，直接手工创建

会话 `ca23d030-f123-45fe-a979-187598de1b35` 开始时，第一次留下的 `_asar` 已存在。实际轨迹中：

1. Agent 再次尝试让 Python 执行 ASAR 虚拟路径。
2. 执行失败后没有查找或复用 `_asar`。
3. Agent 声称“直接手动创建，结构完全符合规范”。
4. 它使用 `mkdir` 和 `write` 创建 `SKILL.md` 与 `.install-meta.json`。
5. 没有成功运行 `init_skill.py`，也没有运行 `quick_validate.py`。
6. 最终中文 UI 显示正常，但系统 Creator 的标准流程并未完成。

这说明 `_asar` 只是偶然遗留目录，不是平台管理的版本化缓存。不同会话会根据模型临场判断走出不同路径，问题比重复解压更严重。

### 产品结论

SealSeek 需要提供从系统 Skill 虚拟位置到外部进程可执行真实路径的正式桥接，或者由产品内部窄范围物化当前版本 helper。不能依赖 Agent 下载 ASAR 工具、完整解压应用或静默手工创建。

## 工具化方式

对于 SealSeek，可使用 `sealseek-chat` 将审计拆成两层：

```bash
sealseek-chat trace <session-id> --target windows-vm --format markdown
sealseek-chat audit <session-id> --target windows-vm --profile auto
```

- `trace` 负责确定性地解析 transcript、关联工具调用与结果、脱敏并生成时间线。
- `audit` 负责检测失败重试、ASAR 执行、完整解压、静默手工创建、验证缺失和成功声明冲突。
- 审计 Skill 负责读取用户目标和上游契约，检查实际输出物并给出最终语义分类。

机器规则不能替代语义审计，语义审计也不能覆盖原始机器证据。

## 回归要求

修复后至少验证：

- 相同用户请求在干净新会话中执行；
- 正确 Skill 被读取；
- 关键 helper 真实成功执行；
- 不发生额外下载、完整解压或权限放宽；
- 正式验证器和端到端输出物检查完成；
- 临时文件被清理；
- 最终声明与工具证据一致；
- 另一台或另一份干净环境可复现。
