# 公司共享 GPU 工作节点与分时调度方法

## 先确认成熟度

本页同时记录两种不同层级，使用时不可混淆：

| 层级 | 定义 | 当前状态 |
| --- | --- | --- |
| 远程 GPU 原型 | 一名或少量受信任用户通过虚拟局域网和 SSH，把任务交给一台 GPU 机器执行 | **已验证**，Real-ESRGAN 超分案例可以运行 |
| 公司级共享平台 | 多人以独立身份提交任务，由服务统一排队、限流、调度、审计和治理 | **尚未建设**，本页只提供目标方法和演进模板 |

现有测试证明的是“异地访问 GPU 和远程执行链路可行”，不代表已经实现全公司 GPU 分时共享。

## 核心判断

公司共享 GPU 不是“让所有人都能 SSH 到一台电脑”，而是把 GPU 包装成一个有边界的任务服务：

```text
用户/Agent
  -> 稳定提交入口
  -> 身份与权限
  -> 任务队列
  -> 调度与资源租约
  -> GPU Worker
  -> 结果存储
  -> 状态、审计与指标
```

网络解决“能不能到达机器”，队列解决“谁先使用 GPU”，应用层权限解决“谁能做什么”，审计解决“发生了什么”。四者不能互相替代。

## 一、先把计算任务标准化

共享之前，先把某项 GPU 能力变成确定的执行器。一个执行器至少需要：

- 稳定命令或 API；
- 明确的输入、输出和参数；
- 模型版本与运行环境；
- 可机器判断的成功、失败和降级状态；
- 超时、清理和幂等策略；
- 可估算的显存、耗时和磁盘占用。

建议统一任务契约：

```json
{
  "job_id": "uuid",
  "requester": "user-or-service-id",
  "executor": "image-upscale",
  "model": "realesrgan-x4plus",
  "parameters": {"scale": 2},
  "input_uri": "object://bucket/input/file.png",
  "priority": "normal",
  "timeout_seconds": 600,
  "submitted_at": "ISO-8601"
}
```

结果不能只有一个文件路径，还应返回：

```json
{
  "job_id": "uuid",
  "status": "succeeded",
  "output_uri": "object://bucket/output/file.png",
  "executor_version": "version",
  "started_at": "ISO-8601",
  "finished_at": "ISO-8601",
  "degraded": false,
  "error_code": null
}
```

如果 AI 超分失败后退回普通插值，必须设置 `degraded: true` 或独立状态。只在终端打印警告会产生“文件存在但任务语义失败”的假成功。

## 二、网络层：用虚拟局域网连接人和 Worker

当 GPU 机器与用户不在同一地点时，可用 Tailscale 之类的 overlay network：

- 每台设备获得稳定的虚拟地址或 MagicDNS 名称；
- 通过 WireGuard 建立端到端加密通道；
- 自动处理 NAT 穿透，无需暴露公网 SSH 端口；
- 无法点对点直连时，可使用加密中继保持可达；
- 通过用户组、设备标签、端口和设备状态约束访问。

推荐角色：

```text
group:gpu-users        可提交任务的员工
tag:gpu-gateway        任务入口
tag:gpu-worker         真正运行模型的机器
group:gpu-admins       运维与应急人员
```

公司级方案中，普通员工宜只访问 `gpu-gateway` 的服务端口；`gpu-worker` 的 SSH/管理端口只允许管理员或网关访问。Tailscale 当前新部署可优先考虑 Grants，但实施时必须以组织当时的官方文档和安全制度为准。

### 为什么不能止于 Tailscale

Tailscale 能控制“谁能连接哪个主机和端口”，但不会自动提供任务排队、公平性、用户额度、模型参数权限、文件保留期、GPU 进程并发或业务审计。这些必须由任务服务负责。

## 三、身份与权限：禁止共享管理员密钥

初步测试可由一个受信任操作者使用独立 SSH 密钥验证链路。面向多人时，应改为：

1. 每个用户使用公司 SSO/Tailnet 身份进入网关；
2. 网关把用户身份写入任务记录；
3. Worker 使用单独的服务身份领取任务；
4. 管理员 SSH 与普通任务提交分离；
5. 禁止把同一管理员私钥复制给所有员工；
6. 模型、优先级、最大输入尺寸和日配额按角色控制。

最小权限原则要求网络授权与应用授权同时成立。

## 四、队列与调度：文件名隔离不等于分时共享

给每个任务生成唯一目录只能避免文件覆盖。若多个请求同时启动 GPU 进程，仍可能发生显存溢出、耗时抖动、桌面任务变慢、长任务独占，以及失败后残留进程或临时文件。

### 单 GPU 的安全起点

- 初始并发设为 `1`；
- 按真实任务压测显存峰值、耗时和温度；
- 只有在执行器支持并行且留有足够安全余量时，才提高并发；
- 显存大任务与小任务可建立不同队列或资源档位；
- 不以 GPU 利用率高作为唯一目标，还要控制失败率和等待时间。

### 最小任务状态机

```text
submitted -> queued -> leased -> running
                           |        |
                           |        +-> succeeded
                           |        +-> failed
                           |        +-> timed_out
                           |        +-> cancelled
                           +-> queued（租约过期后重排）
```

### 推荐调度规则

1. 默认 FIFO，保证简单可解释；
2. 增加用户级并发上限，防止单人占满队列；
3. 使用有限优先级，不允许普通用户无限插队；
4. 对超大任务设置成本权重或单独队列；
5. Worker 领取任务时获得带过期时间的租约；
6. Worker 定期心跳，失联后由调度器回收租约；
7. 重试必须有次数上限并区分可重试与不可重试错误；
8. 取消任务要能终止进程并清理临时文件。

## 五、Worker：把 GPU 机器当执行节点

Worker 的职责应尽量单一：

- 启动时注册 GPU、显存、模型和执行器版本；
- 从队列领取符合资源条件的任务；
- 为每个任务创建隔离工作目录；
- 下载输入、校验类型/尺寸/哈希；
- 执行 GPU 命令并捕获退出码、日志和峰值资源；
- 上传结果并写回状态；
- 无论成功失败都执行清理；
- 心跳中报告可用、忙碌、维护或故障。

不要让客户端直接拼 PowerShell 或 CUDA 命令。执行器命令应固化在 Worker 端，客户端只提交受控参数。

## 六、数据与文件生命周期

任务服务要预先定义输入是否含客户数据、上传下载是否全程加密、输入输出日志各保留多久、临时目录何时清理、用户之间如何隔离、哪些敏感任务不得进入共享 Worker。

最小规则是：每个任务独立目录、默认短期保留、按身份授权下载、过期自动清理、日志不记录原始敏感内容。

## 七、可观测性和容量规划

至少记录提交人、任务类型、排队/开始/结束时间、模型与版本、Worker、显存峰值、结果状态、输入输出大小、错误码和重试次数。

| 目标 | 指标 |
| --- | --- |
| 用户体验 | 排队时间 P50/P95、总完成时间、取消率 |
| 稳定性 | 成功率、OOM 率、超时率、降级率 |
| 容量 | GPU 忙碌时间、显存峰值、每日任务量、队列长度 |
| 公平性 | 用户占用时长、配额命中、最长等待任务 |
| 运维 | Worker 在线率、残留进程、清理失败、磁盘占用 |

扩容判断应来自这些数据，而不是仅凭“感觉机器很忙”。

## 八、四阶段演进路线

### 阶段 0：本机执行

一台机器、一个操作者，先证明模型和命令有效。

### 阶段 1：远程 GPU 原型

虚拟局域网 + SSH/SCP，客户端 CLI 封装远端命令，job_id 隔离文件，适合少量受信任用户验证价值。

**当前 Real-ESRGAN 超分测试处于本阶段。**

### 阶段 2：单 Worker 共享服务

增加 API/CLI 网关、个人身份、中央队列；单 GPU 并发从 1 开始；增加状态查询、取消、超时、审计和自动清理。这是“公司内部可控试运行”的最低形态。

### 阶段 3：公司级共享平台

加入 SSO、角色权限、配额、公平调度、多执行器、对象存储、可观测性、告警、成本与容量规划，以及安全评审、数据分级、SLA 和运维责任人。

### 阶段 4：GPU 资源池

按 GPU 型号、显存、模型缓存和区域调度，支持弹性扩缩、抢占、维护窗口和故障转移。只有业务量和组织复杂度证明必要时才进入该阶段。

## 九、项目启动模板

### 目标契约

- 共享的 GPU 能力是什么？
- 面向哪些用户和任务量？
- 可接受的等待时间和成功率是多少？
- 哪些数据禁止处理？
- 当前只做原型、内部试运行，还是正式平台？

### 技术清单

- [ ] 执行器 CLI/API 已稳定
- [ ] 模型和环境有版本
- [ ] 输入输出契约明确
- [ ] 网络不暴露公网管理端口
- [ ] 用户与服务身份分离
- [ ] 无共享管理员私钥
- [ ] 有中央队列和并发上限
- [ ] 有任务状态、超时、取消和重试
- [ ] 有独立工作目录与清理
- [ ] 有日志、指标和错误码
- [ ] 有敏感数据和保留期规则
- [ ] 有容量压测与回滚方案

### 验收边界

“可以从外地运行一次 GPU 命令”只能验收阶段 1；只有多人身份、排队、公平性、审计、数据治理和运维机制都通过，才能称为公司级共享平台。
